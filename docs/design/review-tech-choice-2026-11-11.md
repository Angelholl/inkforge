## 二、总体判断（先给结论）

方向正确，但有三个“先证明再动工”的关口，否则容易做成一个漂亮但跑不完 20 章的东西：

1. 本地 126B iq3_xxs 的“每章耗时 × 质检重写轮数”必须先有实测基线（R1，[HIGH_RISK_OBJECTION]）。
2. 长任务必须“状态落库 + 独立 worker + 断点续跑”，不能把队列放在 GUI 进程里（决策点 3）。
3. 自动质检必须以确定性校验为主干、模型评分为辅，且重写循环必须有可证明的终止条件（决策点 5）。

## 三、逐决策点评议

### 决策点 1：应用形态与 GUI 技术栈

**我理解的决策**：在 Electron、Tauri、本地服务+浏览器之间选一个承载形态，满足单人 Windows、数小时无人值守、中等 GUI 复杂度。

**立场：支持“本地 headless 服务 + 浏览器 GUI”，反对 v1 选 Tauri，Electron 降级为可选外壳。**

**首选方案**

- 引擎：Node.js 22 + TypeScript，Fastify/Express 提供 REST + SSE（进度流），静态托管前端。
- GUI：React 19 + Vite + Tailwind + TanStack Query（或 tRPC），只做项目/章节/运行/版本/风格档案五类页面。
- 启动：service 进程常驻（托盘或后台 vbs/bat 启动），浏览器打开 localhost；后期需要“像桌面软件”时，再加 Electron/Tauri 壳，壳只负责启动 service + 开窗，不承载业务。

**替代方案**

- Electron 一体：可接受，但必须把生成队列放进独立 child process，主进程只做 IPC。代价是打包体积（本机产物 250MB+）、原生模块 rebuild、auto-update 成本，对单人自用收益低。
- Tauri：不推荐 v1。引擎要用 Rust 重写队列/文件/流式/JSON 修复，生态与参考实现（TS）不匹配，省下的几十 MB 换不来任何需求收益。

**理由与证据**

- 无人值守的第一故障源是 GUI 生命周期：Electron 窗口关闭/渲染进程崩溃若连带主进程，几小时成果直接丢。headless service 从结构上消除这一类故障。
- Pagekin 的“运行侧页 + 失败恢复候选”说明即使成熟实现也需要把运行状态独立管理；headless 更进一步，UI 只是观察者。
- 单人自用不需要签名、自动更新、多平台分发；浏览器 GUI 迭代最快，出问题可直接 curl/看日志定位。
- 本机已装的 Pagekin 是 Electron（书童.exe），其 1.4.0 体积与原生依赖（better-sqlite3/LanceDB）说明 Electron 路线可行但重，不是必须。

**风险**

- 端口冲突/多实例：固定端口 + 单实例锁（pid 文件/命名 mutex）解决；概率中、影响低。
- “不像桌面软件”的心理落差：用启动脚本 + 托盘图标缓解；概率中、影响低。
- 浏览器标签页休眠导致 SSE 断开：服务端以 DB 为真相，重连回放进度即可；概率中、影响低。

### 决策点 2：数据层

**我理解的决策**：为几十万字正文、章节多版本、连续性结构化数据选存储。

**立场：支持 SQLite（WAL）为唯一真相源；明确反对 MongoDB；纯文件只作为导出物，不作为主存储。**

**首选方案**

- 单文件 SQLite（better-sqlite3，WAL，synchronous=NORMAL，busy_timeout），一个项目一个库，或全局一库 + project_id 分区（推荐前者，便于整库备份/迁移）。
- 正文存 TEXT 列；版本 append-only：`chapter_versions(id, chapter_id, parent_version_id, kind[draft|qc|revised|final|manual_edit], content, word_count, run_id, prompt_hash, model, params_json, created_at, status)`，永不 UPDATE 覆盖，只插新版本 + 指针表指向 current。
- 连续性结构化表：`characters`（基础设定 + 当前状态 JSON）、`character_states(chapter_no, ...)`、`foreshadowings(planted_ch, advanced_ch[], resolved_ch, status)`、`chapter_summaries(chapter_no, summary, beats_json, open_threads_json)`、`facts`（可选：地点/物品/时间线）。
- 检索：FTS5 + `tokenize='trigram'` 做中文子串检索（够 MVP）；向量检索（LanceDB/sqlite-vec）推迟到需要“跨全书语义召回”时再加。
- 安全：每次 run 前 `VACUUM INTO backups/xxx.db`，保留最近 N 份；导出 `exports/{book}/{chapter}.md` 作为人类可读快照。
- 迁移：`PRAGMA user_version` + 顺序迁移脚本，不引重型 ORM；SQL + 类型化 mapper。

**替代方案**

- 纯 Markdown/JSON 文件 + 目录结构：人类可读、可 git diff，但跨章查询（伏笔未回收、角色状态演进、版本对比、断点状态机）要靠全量扫描与自建索引，事务性差，Windows 路径/编码/并发坑多。可作为“每周导出快照”，不适合做主存储。
- MongoDB：单人本地多一个服务进程、备份/迁移更麻烦，无事务优势（本场景是强一致的小数据），且会诱导复制 MirrorNovel 的服务端形态——明确反对。

**理由与证据**

- Pagekin 公开 README 明确“Local SQLite database plus per-project folders”，本机构建产物 `.db` 引用 244 次，说明长篇小说场景下 SQLite 已被验证够用。
- 体量根本不是问题：50 万字 UTF-8 约 1.5MB，5 个候选版本也 <10MB；SQLite 的瓶颈在并发写，而本设计天然单写者。
- 版本 append-only 与 Pagekin“草稿全部保留、可回滚为新草稿”一致，且是无人值守场景的硬要求（见 R2）。

**风险**

- better-sqlite3 是原生模块，Node 大版本升级需 rebuild：锁 Node LTS 并在 CI/脚本里固定；概率中、影响低。
- WAL 文件与主库需一起备份：备份脚本用 `VACUUM INTO` 规避；概率低、影响中。
- 单库损坏：定期快照 + 导出 md 双保险；概率低、影响高，故列为验收项。

### 决策点 3：长任务架构（挂机 20+ 章）

**我理解的决策**：进程内队列、独立 worker、还是持久化任务 + 可恢复，以及崩溃恢复与断点续跑。

**立场：支持“DB 持久化 run/step 状态机 + 独立 worker 进程 + 租约心跳”；反对进程内队列作为 v1 形态。**

**首选方案**

- 三层：service（API/SSE/静态页）→ worker（生成执行，concurrency=1，因本地单模型并行只会互相拖慢）→ LLM provider。
- 状态机：`runs(id, book_id, mode, status, created_at, ...)`、`run_steps(id, run_id, chapter_id, step[draft|qc|revise|summarize|finalize], attempt, status[queued|inflight|done|failed|skipped], lease_owner, heartbeat_at, started_at, ended_at, error, output_version_id)`。
- 提交语义：每个 step 完成即短事务写入产物 + 状态，绝不在 LLM 调用期间持有写事务；重试以 (run_id, chapter_id, step, attempt) 幂等键防重复入库。
- 恢复：worker 启动时接管 `inflight` 且 heartbeat 超时的 step（视为中断），从该 step 重跑；已 done 的 step 不重跑；章节级“最后提交版本”即断点。
- 流式中间态：流式 token 周期性落 `partial_outputs`（如每 200 token 或每 5 秒），崩溃后可选择“续写残稿”或“丢弃重生成”；这是 Pagekin `recoveryCandidate` 思路的对应物（其实现区分空输出/源已变更/已处理三种候选）。
- 控制面：暂停（当前章跑完后停）、取消（abort 当前请求）、单章重跑、失败章跳过继续；所有状态经 SSE 推送。
- Windows 专项：worker 独立进程 + supervisor 自动重启（退避）；启动时 `powercfg`/SetThreadExecutionState 阻止睡眠；日志文件滚动；单实例锁。

**替代方案**

- 进程内队列：实现最快，但 UI 关闭/崩溃/重载即中断，恢复逻辑仍要写，等于白做；只可用于 mock 测试。
- 外部消息队列（Redis/BullMQ）：单人本地引入额外服务，收益为 0；反对。
- Windows 计划任务/服务：可作为“开机自启 worker”的补充，但状态真相仍应在 SQLite，不应依赖任务计划的状态。

**理由与证据**

- 需求明确“挂机 20+ 章无人值守”，一轮 10+ 小时；任何依赖 GUI 存活的队列都不可接受。
- Pagekin 运行侧页提供“批量暂停 + 失败运行恢复候选”，说明失败恢复是真实高频需求，不是理论风险。
- 单写者 + WAL 让“service 读、worker 写”的并发模型简单可靠。

**风险**

- worker 与 service 双进程的部署复杂度：用同一 npm workspace、同一启动器解决；概率高、影响低。
- 长请求超时：本地 126B 单章可能 10–30 分钟，超时须按步分级（draft 3600s，qc 900s），并用心跳而非固定总超时；概率高、影响中。
- 断电/蓝屏：已提交 step 不丢，未提交残稿可 salvage；概率低、影响高，列入验收（kill -9 测试）。
- 模型服务重启导致连接中断：provider 层重试 + 章级重跑；概率中、影响中。

### 决策点 4：LLM 接入层与 token 预算

**我理解的决策**：统一 OpenAI 兼容 provider 的设计要点，以及本地慢模型下长上下文的预算与耗时权衡。

**立场：有条件支持“单一 OpenAI 兼容 provider + 角色路由”，条件是按“能力描述符 + 上下文预算装配器 + 前缀稳定”实现；对“沿用默认大上下文整段投喂”明确反对。**

**首选方案**

- 统一 client：`{baseURL, apiKey?, model, timeoutByStep, maxRetries(指数退避+抖动), concurrencySemaphore, stream+abort, usage记账, 请求/响应日志（脱敏）}`。注意：本地端点也可能校验 key（本机 18500 实测返回 `missing or wrong API key`），配置必须允许本地也填 key，不能假设“本地=无鉴权”。
- 能力描述符：`{contextWindow, maxOutput, supportsJsonSchema, supportsPromptCache, notes}`，按 provider+model 配置；预算器据此计算，不写死。
- 角色路由：`planner / drafter / qc / rewriter / summarizer` 各自可绑不同模型；默认全本地，云端可选只接 qc/planner（质量杠杆最大、调用最少）。
- 上下文装配器（核心）：按固定槽位与预算组装，绝不整本送：
  - 稳定前缀（system/硬规则/风格档案/世界观静态）→ 本章蓝图 → 连续性快照（角色状态+未回收伏笔+近 3 章摘要）→ 上一章尾部 1500–2500 字 → few-shot（3 段）→ 本章任务与禁区 → 输出预留。
  - 32k 上下文示例预算：2.5k + 1k + 2.5k + 1.5k + 1.5k + 0.5k + 输出 5k ≈ 14.5k，余量充足。
  - 8k 上下文降级：蓝图 0.5k + 摘要 1k + 上章尾 0.8k + few-shot 1k + 输出 3k，并关闭“整章重写”、改用定点替换。
- 本地模型专项：
  - 前缀稳定（稳定块在前、易变块在后），复用 llama.cpp prompt cache/KV cache；同一本书同一 run 内保持 system 段逐字节一致。
  - 不依赖服务端 context shift（会静默丢早期上下文），客户端硬预算，超限即裁剪。
  - JSON 遵循不可靠（iq3_xxs 尤甚）：QC/摘要优先“分隔符 + 简短字段”纯文本协议，客户端解析 + 一次修复重试；JSON schema 仅对确认支持的云端启用。
  - 采样：创作 temp 0.8–1.0 / top_p 0.9 / repeat_penalty 1.05–1.10；QC temp 0.1–0.3。反重复靠提示词 + n-gram 检测，不靠高惩罚（会伤用词自然度）。
- 耗时策略：预估 = 输出 token / 实测 tok/s；若单章预估 > 阈值（如 45 分钟），自动降级（缩短上下文/跳过二次审稿）或转云端；每章记录实际耗时与 token，供预算器校准。

**替代方案**

- 多 SDK 适配（OpenAI/Gemini/Anthropic 原生）：v1 不做，OpenAI 兼容层已覆盖 Ollama/llama.cpp/vLLM/多数云；Gemini 原生留到确有需求。
- 直接整本/整卷投喂：长上下文模型看似可行，但本地 126B 在长上下文下速度进一步塌陷，且质量并非随上下文线性提升；反对。

**理由与证据**

- Pagekin 明确“只给蓝图+相关角色+世界观+前情摘要+上一章”，是已验证的上下文裁剪范式。
- MirrorNovel 明确长文按 20 段×2 万字采样而非全文入模，并提示“块顺序稳定优先以保前缀缓存”，与本方案一致。
- 本地服务实测需鉴权，说明 provider 抽象不能简化成“本地无 key”。

**风险**

- [HIGH_RISK_OBJECTION] 见 R1：无实测 tok/s 就承诺 20 章连产，属于把工期建在未验证假设上。
- 量化模型的指令遵循与中文长文质量未知：概率高、影响高；缓解=先跑 3 章盲评基线，不达标则 QC/规划上云。
- prompt cache 未命中导致每章重复预填：概率中、影响中；用日志中的 cached tokens 监控。
- 上下文裁剪过度导致“前情断线”：概率中、影响高；用连续性快照的结构化字段兜底，并在 QC 中设“与前文事实冲突”硬检查。

### 决策点 5：自动审稿/质检与重写终止

**我理解的决策**：单模型自审、结构化规则校验、多 pass prompt 链三选一，以及重写循环何时停。

**立场：支持“确定性校验为主干 + 引用证据的结构化 rubric 单 pass + 定点重写”；反对自由发挥式“让模型自己看看写得怎么样”，反对无上限重写。**

**首选方案（分层，成本从低到高）**

- L0 确定性校验（零 token，必做）：
  - 长度区间（目标字数 ±20%）、段落/对话比例、标点与格式异常；
  - 禁用句式/套话表（如“不是……而是……”“这一刻，他明白了”“空气仿佛凝固”等可配置）；
  - 与近 3 章的 n-gram 重合率（防重演，Pagekin 有同类校验思路）；
  - 连续性事实核对：角色生死/位置/称谓/物品、时间线、伏笔状态与本章摘要的 JSON 对账；
  - 蓝图覆盖：本章 must-have beats 是否逐条落地（可用关键词/语义粗匹配，不通过再交 L1）。
- L1 模型质检（单 pass，结构化输出）：固定维度打分 + 每条问题必须引用原文句子 + severity(blocker/major/minor)：设定一致、人物一致、情节推进、文风贴合（含可测漂移指标）、节奏、结尾钩子、重复度。要求“无引用不给分”，显著降低幻觉挑刺。
- L2 门控与重写：
  - 触发：任一 blocker，或 ≥2 个 major，或 L0 硬失败；
  - 重写输入只给“原文 + 问题清单 + 硬事实基线”，不给完整 QC 对话；局部问题用段落定点替换（省时省 token），结构性问题才整章重写；
  - 终止条件（四选一即停）：全部硬检查通过且加权分 ≥ 阈值；轮数达 2；分数较上轮提升 < 5%（无改善）；时间/token 预算耗尽。停止后一律保留当前最佳版本并标 `needs_human`，绝不静默丢章。
- 评审者与写作者尽量不同模型（本地写、云端审，或反过来），降低自偏好；同模型时 QC 换 system prompt 与低温度。

**替代方案**

- 单模型一次自审即通过：省时但基本等于放行，iq3_xxs 的自评能力尤其可疑；反对作为唯一手段。
- 多模型多 pass 链（3+ 次评审）：在本地慢模型上时间成本翻倍，收益递减；不做默认，保留为“云端质检模式”。

**理由与证据**

- Pagekin 文档索引里存在“AI 自审 vs 稿件校验”的争议条目，说明纯自审路线在成熟项目中也未被无条件采信。
- MirrorNovel 自陈“长度校验不是语义校验”“真实质量未评测”，佐证“只用模型打分”不可靠，必须叠加确定性指标。
- 本地模型速度是本项目最稀缺资源，L0 免费、L1 一次、L2 最多两轮，成本结构可控。

**风险**

- 套话表/规则过度导致文本僵硬：规则分“硬禁/建议”两级，建议级只提示不改写；概率中、影响中。
- QC 模型漏检（尤其量化模型）：概率高、影响高；用 L0 兜底 + 抽样人工复核，并记录漏检案例迭代 rubric。
- 重写引入新事实错误：重写后必须重跑 L0，且事实基线只允许来自连续性表，不允许模型“顺手改设定”；概率中、影响高。

### 决策点 6：风格蒸馏

**我理解的决策**：静态离线蒸馏 vs 每章动态注入，以及 few-shot 选择策略。

**立场：支持“离线蒸馏一次 → 不可变风格档案 → 每章确定性轮换注入”；反对每章动态重新蒸馏；入口 A 续写必须不注入风格、改用 voice-match 质检。**

**首选方案**

- 离线蒸馏（每个参考文本一次）：
  - 采样而非全文（MirrorNovel：最多 20 段×2 万字）；
  - 产出结构化档案：视角/时态、句长分布（中位数与分位）、对话占比、比喻与感官密度、常用词/禁用词、段落节奏、章节开头/结尾习惯、情绪基调；外加 8–12 段 200–400 字“金句级”few-shot 样本；
  - 档案带 source_hash、版本号、不可变；生成时记录 `adopted_at_chapter`。
- 注入策略：
  - 每章按章号确定性轮换 3 段（公式 `((N-1) mod count)`），不用随机，保证可复现、可追溯；章节记录本次样本 ID 与版本；
  - 预算：3×约 240–350 字，硬上限 1200 字；
  - 块顺序：硬规则 > 事实/连续性 > 风格档案 > few-shot > 通用写作建议，稳定块在前以保前缀缓存；
  - 规划阶段不注入（只给分析摘要）；续写入口不注入（原作文风优先）。
- 可测漂移：每章计算句长分布、对话比、独特字比、与参考文本的 n-gram/距离指标，超带即作为 QC 的 major 项；这比“感觉不像”可执行。
- 组合挂载：风格 = persona 模板 + 蒸馏档案 + few-shot + 用户禁用表，四个可独立开关的块，各自带预算与优先级；冲突按上述顺序裁决。

**替代方案**

- 每章动态蒸馏参考文本：模型调用翻倍、结果不稳定、无法复现，且慢模型下不可承受；反对。
- 只用“文风形容词”提示（“文笔细腻、节奏紧凑”）：几乎无效，MirrorNovel 的空样本库失败案例已证明会退化为模板腔；反对作为主手段。

**理由与证据**

- MirrorNovel 的完整设计（persona 六轴、不可变 revision、轮换公式、plan 不注入、导入续写不注入、3×240 字预算、按章节记录样本）是本决策最直接的证据，且其文档同时给出了失败教训：样本库为空时风格注入无可见效果、长度校验非语义校验、无抄用审计。这些应作为我们的前置门槛与回归项。
- 入口 A 的本质是“模仿既有文本”，此时参考文本本身就是最强风格锚，再注入外部风格只会打架；因此“续写不注入、改用 voice-match 质检”是需求层面的正确取舍。

**风险**

- 风格档案过度抽象成形容词：蒸馏 prompt 必须要求“可量化规则 + 原文例证”，否则无效；概率中、影响高。
- few-shot 触发抄用：概率中、影响中；加“禁止连续 15 字以上重合”的检测（L0），并在提示中明确“只校准表达，不提供情节”。
- 轮换导致章间风格跳动：概率低、影响中；同书内限制在 2–3 个风格版本，切换须显式记录。

### 决策点 7：MVP 切法

**我理解的决策**：先做什么、后做什么，第一版最小闭环。

**立场：支持“先纵向打通单章闭环 + 先证队列可恢复”，反对先做平台化（多书/多模型/向量库/编辑器）。**

**MVP（v0.1）范围**

1. mock provider（固定文本/可控失败注入）+ 单章管线：上下文装配 → 初稿 → L0 校验 → L1 质检 → ≤1 次重写 → 版本入库 → 导出 md。
2. 3 章顺序队列（暂停/取消/单章重跑/断点续跑），kill -9 后可恢复。
3. 最小连续性：章节摘要 + 角色状态 JSON + 上章尾部；摘要由 LLM 生成，允许人工修正。
4. 最小风格：一个静态档案 + 固定 3 段 few-shot；入口 A 变体为“不注入”。
5. 最小 UI：章节列表、运行面板（进度/日志/取消）、正文查看、版本列表与回滚、重跑按钮。

**v0.2**：20 章批量、失败章跳过、自动伏笔/角色状态抽取、预跑快照备份、耗时/token 仪表盘。
**v0.3**：风格轮换与漂移检测、云端 provider 与角色路由、版本 diff/段落定点重写 UI。
**明确不做（直到有真实需求）**：向量库、多书并行、EPUB 导入、移动端、自动更新、多人协作。

**MVP 验收门（可执行）**

- mock 全链路 <10 秒跑通，覆盖失败/重试/恢复分支；
- 真模型连续 3 章无人值守 ≥2 小时，无人工干预；
- 运行中 kill worker，重启后从最后提交步续跑，无重复章、无版本丢失；
- 人为注入“永远不合格”的 QC，重写 2 轮后必停并标 needs_human；
- 关机/睡眠设置生效，8 小时挂机不断；
- 导出 md 与 DB 当前版本逐字一致；
- 单章耗时与 token 有记录，能算出 20 章总时长。

**理由**

- 最大技术风险是“长任务可恢复”和“慢模型单章时长”，必须在第一版就被真实压测，不能推到 v2。
- mock provider 是慢模型下的必需品：管线迭代不应每次等 20 分钟。

### 决策点 8：协议合规（GPL/AGPL 边界）

**我理解的决策**：只借鉴思路、代码主体重写，是否需要额外注意。

**立场：支持当前计划，但必须把“只读文档、不抄任何文件/提示词/schema”落成可审计的纪律。**

**首选方案**

- 参考方式限定：只读 README、ADR 标题与结论、docs 中的设计描述、公开 issue；不 clone 到工作区、不 vendor、不复制任何源文件/DDL/UI 文案/提示词文件。
- 自己撰写全部 prompt，并要求 git 历史能证明独立创作；建立 `docs/third-party-references.md`，记录参考日期、参考点（仅思路）、不复制声明。
- 提示词是最高风险项（极易手滑粘贴），单独设 review 检查：提交前比对是否与上游措辞逐句相同。
- schema/表结构按本报告建议独立设计，不照搬 Pagekin/MirrorNovel 的命名与字段组合。
- 依赖许可：better-sqlite3(MIT)、React(MIT)、Fastify(MIT)、LanceDB(Apache-2.0) 均可按需选择；GPL/AGPL 传染只来自“复制其代码/文件”。

**法律面判断（非法律意见）**

- 单人本地使用不构成“分发”，GPL 义务不触发；AGPL 的网络条款针对向公众提供服务，本地 localhost 自用不触发。
- 但计划是重写且可能未来开源，clean-room 纪律决定你能否自由选许可证；现在留证成本极低，事后补证几乎不可能。

**风险**

- 复制提示词/文档段落：概率中、影响中（若未来分发则可能被迫 GPL/AGPL，或引发争议）。
- 过度“参考”目录结构与测试用例：概率低、影响中；用独立设计规避。

## 四、跨决策重大风险（需主模型明确回应）

**R1 [HIGH_RISK_OBJECTION] 把“20+ 章无人值守”的可行性建立在未实测的本地 126B iq3_xxs 上。**
影响：工期、验收标准、整体形态（是否需要云端兜底）全部取决于单章耗时与质量。按 3000 中文字≈4500 输出 token 估算：5 tok/s 时单章初稿约 15 分钟，加一次质检与一次重写约 35 分钟，20 章≈12 小时；若仅 2 tok/s，则 20 章>24 小时；若 15 tok/s，则约 4 小时。差距是 6 倍，不能靠猜。
要求：动工前用真实模型跑 1 章 + 记录 tok/s、首 token 延迟、JSON 遵循率；并做 3 章盲评（连贯性/文风/事实一致性）决定 QC 是否上云。验证责任方：主模型/执行者；不满足则回退为“先做 mock 管线 + 云端小模型验证闭环”。

**R2 [HIGH_RISK_OBJECTION] 无人值守下的数据安全：任何“就地覆盖正文”的设计都是不可逆操作。**
要求：版本 append-only、run 前 `VACUUM INTO` 快照、导出 md、重写后保留原版本；验证方式=kill -9 + 回滚演练。若 v1 计划 UPDATE 覆盖章节内容，我反对放行。

**R3 上下文与速度的负反馈：上下文越长越慢，慢又逼你砍上下文，砍多了断线。**
缓解：结构化连续性快照（摘要/角色状态/伏笔）承担“记忆”，而不是靠堆原文；QC 增设“与前文事实冲突”硬检查。验证：连续 5 章后抽查第 5 章是否与前 4 章事实一致。

**R4 质检的“假通过”风险：量化模型当裁判容易放行或挑无关痛痒的毛病。**
缓解：L0 确定性规则占主导、L1 必须引用证据、阈值与轮数上限、抽样人工复核并记录漏检率。验证：准备 10 个已知缺陷的历史章节做回归集，测 QC 召回率。

无 [DEPENDENCY-IMPACT]：意向书明确技术栈未预设，本次无“已拍板决策”被推翻；若后续决定“QC 一律用本地模型”，则该决定会与 R1 的云端兜底结论产生依赖，届时应复议。

## 五、整体推荐架构摘要（≤15 行）

1. 形态：headless 本地服务（Node 22 + TS + Fastify，REST+SSE）+ 浏览器 GUI（React 19 + Vite），Electron/Tauri 仅作后期外壳。
2. 进程：service（API/静态页/SSE）+ worker（生成队列，concurrency=1）+ supervisor 自动重启；启动器阻止系统睡眠。
3. 数据：单文件 SQLite（WAL）为唯一真相源；正文 TEXT + append-only `chapter_versions`；连续性表（角色状态/伏笔/章节摘要）；FTS5 trigram 检索。
4. 任务：DB 持久化 run/step 状态机 + 租约心跳；每步短事务提交；崩溃从最后提交步续跑；残稿可 salvage。
5. 安全：run 前 VACUUM INTO 快照、导出 md、永不就地覆盖、单实例锁。
6. LLM：统一 OpenAI 兼容 client（本地也支持 apiKey）+ 能力描述符 + 角色路由 + 上下文预算装配器；稳定前缀在前以复用 KV cache。
7. 预算：32k 上下文下 固定前缀2.5k/蓝图1k/连续性2.5k/上章尾1.5k/few-shot1.5k/输出5k；8k 时降级并改定点重写。
8. 质检：L0 确定性（长度/重复/套话/事实/蓝图覆盖）→ L1 引用证据的结构化 rubric → 门控 → ≤2 轮重写（局部定点替换优先）→ needs_human。
9. 风格：离线蒸馏为不可变档案（量化规则+8–12 段样本）；每章确定性轮换 3 段；入口 A 不注入、改用 voice-match 质检。
10. MVP：mock provider 打通单章闭环 → 真模型 3 章无人值守 → 20 章批量与自动摘要；先证恢复，再谈规模。
11. 合规：只读文档不抄代码/提示词/schema，留 `third-party-references.md` 存证。
